1. Le projet en une page

Le besoin. Sous IFRS 17, un actuaire évalue chaque groupe de contrats d'assurance : il lit l'état du portefeuille (primes, sinistres, frais, unités de couverture, taux), calcule les flux de trésorerie d'exécution, l'ajustement pour risque (RA) et la marge sur services contractuels (CSM), retrouve dans la norme les règles qui fondent chaque traitement, puis rédige une note justifiée et la fait valider. C'est long, répétitif et sensible aux erreurs de saisie.

Ce que fait IFRS 17 Copilot. Un document arrive (e-mail, formulaire, site web ou webhook) ; n8n le confie à une API ; six agents spécialisés le lisent, calculent, cherchent dans la norme, vérifient et rédigent ; la note actuarielle (9 à 11 pages A4) part par e-mail en HTML et en PDF. Si un contrôle échoue, un valideur reçoit la note provisoire et un formulaire pré-rempli, corrige, approuve ou rejette. Tout est inscrit dans une piste d'audit infalsifiable. Un Copilot répond ensuite aux questions « et si… » sur le dossier.

Le principe qui a guidé tous les choix : le LLM lit, cherche et rédige ; il ne calcule jamais, et chacune de ses sorties est contrôlée par le code.

2. Méthode de travail

La règle des trois preuves. Aucun choix technique n'est gardé sans une source (documentation, cours, article), une mesure ou un test, et une décision écrite dans docs/decisions.md : options comparées, critères, preuve, statut (proposée, validée, rejetée, remplacée). Chaque échec va dans docs/failures.md : attendu, obtenu, cause, décision, leçon.

Mesurer avant de garder. Chaque amélioration est mesurée contre la version précédente, sur le même jeu, avec un intervalle de confiance quand c'est possible (bootstrap apparié). Une méthode qui ne gagne pas est rejetée et documentée, son code conservé pour la comparaison.

Ne pas s'ajuster sur le test. Les jeux ont des rôles fixés d'avance : un jeu de mise au point pour développer, des jeux de test mesurés une seule fois par méthode. Les 30 cas pratiques puis les 10 questions de test du Copilot ont été gelés dans Git avant tout développement, avec leur empreinte SHA-256 vérifiée par un test.

Prompts versionnés. Une version publiée n'est jamais modifiée ; chaque nouvelle version change une seule chose, motivée par des échecs observés, et elle est mesurée sur le même jeu.

Outils de développement. Git et GitHub (une branche par tâche, relecture), GitHub Actions (ruff puis pytest avec LLM_PROVIDER=fake, puis l'évaluation du routeur), pre-commit (ruff, nbstripout, détection de clé privée, gros fichiers, YAML et JSON valides). Python 3.11+ en venv, Node.js 24 pour n8n, sans Docker (machines Windows hétérogènes, D-001). Colab (GPU T4) pour le fine-tuning, une RTX 3050 pour le reranker.

Honnêteté. Les cas de test ont été rédigés avec l'aide d'un LLM (Claude), puis relus et validés par l'équipe (cas pratiques : 30/30). Les scores obtenus sur un jeu qui a servi à corriger (Copilot v3) sont signalés comme optimistes.

4. Architecture technique

{FIG1}

Parcours d'un dossier, étape par étape.

  1. Un e-mail dont l'objet contient « IFRS17 » arrive (ou un formulaire, un webhook, le site) ; n8n extrait chaque pièce jointe PDF, PNG ou JPEG.
  2. Le nœud « Paramètres » ajoute l'adresse du valideur, l'URL de l'API et le jeton ; le Switch envoie l'élément dans la branche « dossier ».
  3. n8n appelle POST /v1/case (multipart) avec le canal et le déposant ; l'API inscrit le dossier au registre (empreinte SHA-256 du document).
  4. Extracteur : PDF à couche texte → gpt-oss-120b ; scan ou photo → Gemini (deux lectures). Chaque chiffre doit être retrouvé dans le document ; sinon une relance, puis « à vérifier ».
  5. Calculateur (Python) : valeurs actuelles, RA et son niveau de confiance, CSM ou perte, écoulement, projection, sensibilités.
  6. Chercheur RAG : 2 ou 3 questions adaptées au dossier (déficitaire ou non), réponses citées ; vérificateur : chaque phrase jugée ; une correction au plus.
  7. Rédacteur : le code écrit tableaux et graphiques ; le LLM écrit le résumé et le commentaire, contrôlés nombre par nombre.
  8. Statut : note prête, validation humaine (au moins un contrôle non passé) ou document illisible.
  9. Note prête : n8n télécharge le PDF (/note.pdf) et envoie la note au déposant.
  10. Validation humaine : n8n appelle son propre webhook de validation (une exécution par dossier), envoie la note provisoire au valideur puis l'e-mail « Vérifier les données », et attend.
  11. Le valideur corrige le formulaire pré-rempli et approuve : /v1/case/validated recalcule tout ; la note validée part avec son PDF, le déposant en copie. Rejet : inscrit au registre, e-mail de rejet.
  12. Chaque action (dépôt, analyse, e-mail, approbation, rejet) est un événement chaîné dans la piste d'audit.

Les 37 endpoints de l'API, par famille : santé (/health) ; norme (/v1/route, /v1/search, /v1/ask, /v1/ask/audio) ; calcul (/v1/csm/compute, /v1/csm/rollforward, /v1/paa/position) ; documents et dossiers (/v1/extract, /v1/case/document, /v1/case, /v1/case/stream, /v1/case/validated, /v1/samples) ; Copilot (/v1/copilot, historique, rejeu, effacement de la mémoire) ; registre (/v1/cases, détail, note HTML et PDF, rejet, événements, tableau de bord) ; audit (/v1/audit, /v1/audit/verify) ; comptes (connexion, déconnexion, profil, comptes) ; site (/, /app/).

5. Les composants en détail

5.1 Moteur de calcul (engine/)

Ce qu'il fait. Modèle général (BBA) : primes en début de période, sorties en fin, facteurs d'actualisation par taux spot, RA en pourcentage des sorties actualisées, CSM initiale (§38) ou composante de perte (§47), écoulement avec intérêts au taux bloqué (§44(b)), ajustements pour services futurs (§44(c)), recouvrements (récupération, subrogation) comptés en entrées de trésorerie encaissées en fin de période (B65 k, D-071) et libération par unités de couverture (§44(e), B119). Modules ajoutés : projection du compte de résultat et du passif (B124), six chocs de sensibilité et seuils de bascule, duration (analysis.py) ; niveau de confiance du RA par quantile d'une lognormale (risk.py, §119) ; modèle pluriannuel avec OCI et écarts d'expérience (bba.py) ; PAA (paa.py).

Comment il est prouvé. 8 tests contre des calculs faits à la main et écrits dans docs/engine_hand_calcs.md ; 11 tests contre les exercices chiffrés du cours IFRS 17 de l'équipe (retrouvés à l'euro près) ; tests de cohérence de la note (passif rapproché période par période, extinction de tous les postes, produits = primes sans actualisation) ; 3 tests du niveau de confiance ; validation des résultats par l'enseignant (D-069).

5.2 Extracteur multimodal (multimodal/)

Entrées. PDF à couche texte (pdfplumber : texte et tableaux remis dans l'ordre de la page, cellules séparées par « | »), scans et photos (rendu des pages, Gemini Flash), mode hybride (image contrôlée par la couche texte), classeurs Excel et CSV (cellules converties en tableau, provenance à la cellule, formules sans valeur et feuilles cachées signalées, D-079). Le mode est choisi par le document : au moins trois nombres dans la couche texte → texte.

Contrôles. Ancrage : chaque chiffre extrait doit exister dans le document, ou être la somme de deux montants du tableau (sinistres + frais) ; un recouvrement peut être lu dans sa colonne ou comme un sinistre négatif (D-071) ; sinon une relance avec la liste des problèmes, puis « à vérifier ». Plusieurs groupes de contrats détectés → arrêt et validation humaine. Mode vision : seconde lecture d'une image nettoyée (niveaux de gris, contraste, netteté) ; divergence → humain. Document tronqué signalé. Depuis D-067, la page et le tableau de chaque donnée sont enregistrés et affichés dans la note.

Évaluation. 15 documents propres (mises en page variées : lignes, colonnes, récit, milliers, scans) et 10 pièges : ligne « Total », RA absent, instruction cachée dans le document, unités dans les en-têtes, tableau en page 2, photo dégradée, colonne « Total des sorties », montants en millions, unités de couverture absentes, deux groupes. Mesure principale : les cas dangereux (donnée fausse marquée « ok »).

5.3 Base de connaissances et recherche (rag/)

Corpus. Règlement (UE) 2021/2036, PDF de 77 pages, 397 paragraphes (corps, annexes A, B, C) ; annexe D exclue. Ingestion dédiée : marges, polices, colonnes, notes de bas de page, intertitres hiérarchiques ; manifeste versionné, PDF hors Git.

Découpage. A : 512 tokens, chevauchement 64 (138 morceaux). B : un paragraphe par morceau avec son chemin dans la norme (380 morceaux, 127 tokens en médiane). B retenu : rappel à 1 000 tokens 0,757 contre 0,493 (dense, mise au point), deux fois moins de texte envoyé, citation exacte.

Recherche. BM25 écrit à la main (analyseur français, racinisation légère), BGE-M3 dense (1 024 dimensions), fusion RRF (k = 60) de 30 candidats par liste, glossaire de sigles, top-k = 5, filtre de zone ; Qdrant embarqué (collection liée à l'empreinte des textes) ; options : index de questions, graphe des 790 renvois écrits de la norme, reranker bge-reranker-v2-m3 sur 20 candidats. Configuration retenue : agent de recherche LangGraph (planifier en raisonnement en recul, chercher, noter chaque passage, au plus une nouvelle recherche).

5.4 Agent RAG et vérificateur (agents/rag_agent.py, verifier.py)

L'agent répond uniquement à partir des 5 extraits, entre délimiteurs, en citant les paragraphes. Le code vérifie que chaque paragraphe cité est dans les extraits et que chaque citation entre guillemets y est recopiée mot pour mot ; une correction, puis retrait, puis refus. Le vérificateur (gpt-oss-120b) juge chaque phrase : soutenue ? portée respectée ? En v2, il recopie la preuve, que le code retrouve dans le paragraphe. Un juge indisponible bloque le dossier.

5.5 Routeur (agents/router.py)

Classe la demande en quatre intentions (question sur la norme, document, calcul, hors périmètre) ; le code en déduit les étapes. Salutations traitées sans LLM ; questions générales sur IFRS 17 complétées par le §1.

5.6 Rédacteur et note actuarielle (writer.py, note_report.py)

Page de garde, sommaire, 10 sections (résumé exécutif, objet et méthode, données, hypothèses référencées, évaluation initiale, écoulement de la CSM, projection, sensibilités et seuils, fondements cités, contrôles, limites et validation), annexes (traçabilité : empreinte, versions des prompts et des modèles ; glossaire), graphiques SVG. Le LLM n'écrit que le résumé et le commentaire ; chaque nombre doit venir des faits du moteur, chaque paragraphe des passages vérifiés, la double négation est refusée par le code ; sinon le texte est écrit par le code.

5.7 Orchestrateur (agents/orchestrator.py)

Enchaîne les agents, mesure et journalise chaque étape (agent, statut, durée), notifie l'interface en direct, décide du statut. Réponses de référence (vérifiées une fois, relues par un humain) pour les questions fixes : moins d'appels, même niveau de contrôle. Questions à la norme en parallèle disponibles (désactivées après mesure).

5.8 Copilot (agents/copilot.py, memory.py)

Boucle ReAct LangGraph décider → agir → vérifier ; 7 outils en lecture seule (données, scénario, sensibilités, niveau de confiance, projection, recherche dans la norme, mémoire) ; arguments validés par Pydantic ; 5 appels au plus ; chaque nombre de la réponse doit venir d'un outil. Mémoire de travail (état du graphe), épisodique (échanges contrôlés stockés au registre, 3 derniers en contexte, les autres par l'outil de rappel), sémantique (décision du valideur), procédurale (prompts). Checkpointer SQLite : trajectoire visible, rejeu depuis un point de reprise (rôle valideur, inscrit dans l'audit).

5.9 Voix (/v1/ask/audio)

Whisper large-v3-turbo (Groq), français forcé, consigne de vocabulaire IFRS 17 ; la transcription suit la même chaîne qu'une question écrite.

5.10 n8n (workflows/ifrs17_copilot.json)

Un seul workflow, généré par workflows/generer.py à partir des paramètres lus dans le code source de n8n 2.42.3. Déclencheurs : IMAP, formulaire, webhook de dépôt, webhook de validation, santé toutes les 15 minutes (alerte au changement d'état seulement), rapport du lundi, Error Trigger (workflow d'erreur interne, sans réglage). Branches avec sortie d'erreur ; traces d'audit qui ne bloquent jamais un envoi ; note PDF jointe ; valeurs d'exemple dans le fichier exporté, aucun identifiant.

5.11 Registre, comptes et sécurité (core/registry.py, api/security.py)

SQLite : dossiers (canal, déposant, empreinte, statut, chiffres, note, coût), événements chaînés par SHA-256 (/v1/audit/verify), comptes à trois rôles, mots de passe PBKDF2-SHA256 (200 000 itérations), blocage de 5 minutes après 5 échecs, sessions de 8 heures (empreinte seule stockée), jeton machine pour n8n. Fichiers limités à 10 Mo, type reconnu par le contenu.

5.12 Interface web (api/web/)

Page de présentation publique et espace de travail : vue d'ensemble, registre filtrable, fiche dossier (cycle de vie, synthèse chiffrée, note, données à approuver, Copilot, piste d'audit), nouveau dossier suivi en direct, assistant normatif écrit ou dicté, simulateur (BBA pluriannuel, PAA), administration. HTML, CSS et JavaScript sans dépendance, polices auto-hébergées, thème sombre, recherche Ctrl K, utilisable sur téléphone.

5.13 Serveur MCP (api/mcp_server.py)

JSON-RPC 2.0 sur stdio, écrit sans dépendance ; 9 outils en lecture seule, ressources (notes, paragraphes du règlement), deux prompts ; versions du protocole 2024-11-05 à 2025-11-25 ; essayé avec le client officiel du SDK Python MCP.

5.15 Actuariat (actuariat/, engine/paa.py, engine/cloture.py)

Chain Ladder et sélection des dossiers comme le script R de l'équipe (double calcul : 50/50 identiques) ; calibration de la volatilité du RA par back-testing (écart-type robuste de ln réel/attendu) ; registre des hypothèses versionné cité dans chaque note ; PAA comparée au modèle général (même résultat total, testé) ; première clôture : écarts d'expérience en résultat, révisions au taux bloqué affectées aux services futurs (CSM) ou passés (charges), effet des taux en charges financières, rapprochement du passif exigé exact ; note de clôture écrite par le code seul.

5.14 Note en PDF (core/pdf.py)

Edge, Chrome ou Chromium en mode headless impriment la note HTML (graphiques SVG et règles d'impression compris) ; profil temporaire, délai maximal ; sans navigateur, l'API répond 503 et l'e-mail part quand même.

10. Échecs rencontrés et leçons

Les 28 échecs sont décrits en entier dans l'annexe B. Les leçons qui ont le plus changé le projet :

  • Mesurer l'extraction avant d'accuser la recherche (F-003) : la moitié des termes de la norme étaient coupés par pypdf.
  • Un mécanisme de secours doit être visible (F-008) : le routeur LLM échouait en silence et l'heuristique prenait le relais, ce qui faussait la mesure.
  • Vérifier les modèles réellement accessibles (F-009) : Llama était documenté mais inaccessible avec la clé gratuite.
  • Une citation vérifiable n'est pas forcément juste (F-011) : un paragraphe réel, mais qui vise un cas particulier.
  • Un jeu écrit par l'équipe surestime la qualité (F-012) : d'où le quiz du cours et les cas pratiques gelés.
  • Deux corrections indépendantes qui ne bougent pas le plafond désignent une autre cause (F-013) : d'où l'agent de recherche qui raisonne avant de chercher.
  • Quand un défaut revient malgré le prompt, le faire vérifier par le code (F-017).
  • Un jeu qui a servi à corriger ne mesure plus rien (F-018) : Copilot 16/16 en mise au point, 9/10 sur des questions gelées.

11. Limites, dernières mesures et suite

Campagne du 21/10 (D-070, D-071). Critères fixés avant la mesure. Volume : 0 cas dangereux sur 150 documents jamais vus, soit un vrai taux inférieur à 2,0 % avec 95 % de confiance. Montants réels publics (CAS) : un premier lot a donné « 54 dangereux » pour une CSM juste 58/60 ; l'écart venait de la mesure (taux unique contre courbe plate) et de la lecture des tableaux sans grille (F-019). Les deux ont été corrigés puis remesurés sur un nouveau tirage : 60/60, 0 dangereux (borne 4,9 %), 1,2 s par document. Les cohortes à paiements négatifs, d'abord écartées, sont devenues des recouvrements (B65 k) : nouveau lot, 60/60, 0 dangereux, sans régression sur les jeux de référence. Les 50 PDF du script R de l'équipe, lus par le LLM : CSM juste 50/50, 0 cas dangereux, 0 fausse alerte ; au total, 0 cas dangereux sur 320 documents jamais vus (borne à 95 % : 0,9 %). Tableurs (D-079), premier lot de 21 classeurs : CSM juste 17/19, mais 1 cas dangereux — un montant au format pourcentage accepté parce qu'il figurait bien dans le document (F-021) ; d'où un contrôle de vraisemblance pour tous les formats (D-080) ; jeu corrigé de 22 classeurs : CSM 19/19, 3/3 alertes, 0 cas dangereux, et aucune régression sur les PDF. Document à deux groupes (dur10) de bout en bout : deux notes justes au centime dans une note combinée, sans validation humaine. Images de pages lues en mode vision : CSM 4/4, dur10 en alerte. Charge : 5 dossiers complets à la suite en 24 s de médiane (46 s au plus), 3 simultanés sans erreur. Restent à mesurer : photos réelles au téléphone, mode vision sur les données réelles, et les prompts d'extraction v4 (plusieurs groupes, frais d'acquisition, branche).

Dernières mesures (20/10). Appel unique contre chaîne (D-066) : la chaîne trouve la CSM au centime 22 fois sur 22, l'appel unique 3 fois (21 à 1 % près), avec 19 cas dangereux contre 0. Copilot sur 10 questions gelées (D-068) : 9/10, 8/10 à la relecture ; les deux défauts (F-018) sont des pistes pour une v4, à mesurer sur un nouveau jeu.

Ajouts du 24/10 (D-081 à D-085). L'unité des montants doit être écrite dans le document (D-081) : une erreur d'unité multiplie la CSM par 1 000 sans changer aucun chiffre, l'ancrage ne la voyait pas ; vérifié sans fausse alerte sur 187 documents connus, 338/338 erreurs simulées détectées. La volatilité et le niveau de confiance que le document annonce pour son RA sont lus et rapprochés du registre (D-082) : pour le dossier A du camarade, son RA de 7,87 % est bien au quantile 75 % avec son CV de 12,41 %, mais à 65 % avec la volatilité du registre (35 %) ; la note le dit, l'actuaire tranche. Le passif pour sinistres survenus d'un triangle (dossier C) est désormais calculé (D-083) : Chain Ladder et erreur de Mack reproduisent l'article de Mack (1993) au franc près ; dossier C : LIC 17 634,74. Un premier calcul de référence du dossier C, fait à part et non validé, était faux (F-022). Mesures du 24/10 avec gpt-oss-120b : aucune régression de l'extraction (15/15 ; 7 réussis et 3 alertes ; 50 PDF du script R, CSM 50/50, 0 dangereux) et aucune fausse alerte d'unité sur ces 75 documents ; triangles CAS lus par le LLM : triangle juste 7/7, LIC au centime 7/7, 0 cas dangereux, deux fausses alertes corrigées (F-024) ; dossier C lu par le LLM : LIC 17 634,74. Copilot v4 sur 10 questions neuves gelées (D-084) : 8/10, mais un piège d'injection obéi et accepté par le contrôle (F-023) ; garde-fous ajoutés par le code (D-086) : 5 pièges neufs, gelés avant la mesure, tous refusés. Les mesures qui demandent la clé Groq, un téléphone ou un autre membre de l'équipe sont décrites dans docs/protocole_mesures_equipe.md (D-085).

Limites connues. Recherche encore imparfaite sur les questions formulées loin du vocabulaire de la norme (quiz 0,400) ; vérificateur utile mais faillible (kappa 0,46) ; jeux de référence petits (le volume et les montants réels viennent de notre propre générateur : valeurs nouvelles, mises en page connues ; seuls 22 documents portent des recouvrements, borne 12,7 %) ; volatilité du RA calibrée sur des compagnies américaines ; pièges d'injection mesurés sur 5 cas seulement ; un dossier prend 1 à 3 minutes sur les offres gratuites ; formulaire de validation sur localhost.

Passage en production, marche à suivre. HTTPS par tunnel ou reverse proxy et WEBHOOK_URL dans n8n ; API payante avec contrat de non-réutilisation des données, ou modèle hébergé en interne ; PostgreSQL au-delà d'une équipe ; test de charge ; sauvegarde du registre. Suites fonctionnelles : une note par groupe de contrats ; documents photographiés en conditions réelles comme nouveau jeu de test ; indexation des exemples illustratifs d'IFRS 17.
